01 • System Blueprint

1. Overview

The purpose of Task 04 was to engineer a browser-based IoT monitoring and control dashboard powered by Firebase Realtime Database and deployed globally via Firebase Hosting.

The web application displays real-time ambient telemetry—specifically Temperature, Humidity, and Light Level—and provides a real-time binary toggle switch for an electrical Bulb. Rather than forcing the browser to maintain a fragile peer-to-peer connection with embedded microcontroller silicon, the frontend connects directly to Firebase using the official Firebase JavaScript SDK v10.

Figure 4.1 — Complete 3-Tier Data Synchronization Pipeline: Web Browser DOM Bindings, Firebase RTDB Cloud State, and ESP32 Physical Tier.
CLIENT TIER
Reactive Web Interface
Constructed purely in vanilla HTML/CSS/JS. Binds directly to DOM targets using onValue() event listeners to render incoming environmental values without page refreshes.
CLOUD TIER
Shared Cloud Database State
Firebase Realtime Database persists the shared JSON tree, managing bidirectional WebSocket channels that broadcast mutations instantaneously across connected subscribers.
EDGE TIER
Physical Hardware Node
The ESP32 microcontroller reads physical transducers (DHT11, LDR) and executes relay actuation, communicating exclusively through cloud database endpoints.
02 • Design Intent

2. What I Was Trying to Build

The engineering objective was to eliminate direct hardware coupling. Instead of requiring a client to know the ESP32's local IP address or maintain an open socket directly to an embedded web server, the user interacts seamlessly through a shared cloud state repository:

DOWNLINK INGESTION
Continuous Telemetry Streaming
Open the dashboard from any browser → Establish persistent WebSocket connection → Receive real-time telemetry snapshots → Render live values dynamically.
UPLINK ACTUATION
Deterministic Actuator Mutation
User toggles bulb switch → JavaScript fires set() mutation → Cloud writes 1 or 0 → Hardware subscriber catches event and switches relay.

05 • Cloud Data Contract

5. Firebase Database Structure

The database schema is organized as a shallow, deterministic JSON hierarchy partitioning read-only telemetry from write-enabled control parameters:

Figure 4.3 — Firebase Realtime Database JSON Schema Tree: Structured Partitioning of Telemetry Streams and Actuator Directives.
PATH: telemetry/live/
Read-Only Telemetry Partition
Contains current environmental sensor outputs (temperature, humidity, light). Consumed by the web dashboard as read-only event streams. Written exclusively by microcontroller firmware.
PATH: controls/bulbState
Read-Write Actuation Partition
Holds the target binary actuator state (1 = ON, 0 = OFF). Mutated by the dashboard toggle switch and consumed by the ESP32 relay driver.
06 • Dual Communication Pipeline

6. Complete Data Flow Pipeline

The system maintains two independent, non-interfering data streams across the shared cloud database:

Figure 4.4 — Dual Operational Pathways: Asynchronous Downlink Telemetry Ingestion vs Instantaneous Uplink Actuation.
STREAM A
Downlink Sensor Telemetry Pipeline
Sensors sample ambient physical conditions → ESP32 serializes JSON → Pushes to telemetry/live → Firebase broadcasts over WebSocket → onValue() unblocks → DOM text nodes update.
STREAM B
Uplink Actuator Control Pipeline
User clicks Bulb Toggle → change event fires → set(bulbRef, 1 or 0) mutates database → Cloud updates controls/bulbState → Hardware listener catches event → Relay switches AC load.
07 • Protocol Architecture

7. Reactive Event Streaming vs HTTP Polling

Traditional web architectures often query REST APIs using periodic setInterval() polling loops. This approach incurs heavy HTTP header overhead, wastes mobile client bandwidth, and produces choppy, delayed UI rendering.

Figure 4.5 — Protocol Comparison: Traditional HTTP Polling vs Firebase Reactive WebSocket Push Architecture.
Traditional HTTP Polling (Obsolete)
Dispatches repetitive GET requests every N seconds. Massive TCP handshake overhead, redundant empty responses, battery drain, and inevitable notification latency.
Firebase Reactive Streams (Task 4)
Maintains a single persistent WebSocket connection. Zero idle bandwidth. The cloud server pushes byte payloads strictly when database values mutate.

11 • Production Code

11. Complete Frontend Source Code

File: index.html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Smart IoT Dashboard</title>
</head>
<body>
  <h1>Smart IoT Dashboard</h1>
  <p>Temperature: <span id="temp">--</span> &deg;C</p>
  <p>Humidity: <span id="hum">--</span> %</p>
  <p>Light level: <span id="light">--</span> %</p>
  <label><input type="checkbox" id="bulbToggle"> Bulb</label>

  <script type="module">
    import { initializeApp } from "https://www.gstatic.com/firebasejs/10.12.0/firebase-app.js";
    import { getDatabase, ref, onValue, set } from "https://www.gstatic.com/firebasejs/10.12.0/firebase-database.js";

    const firebaseConfig = {
      apiKey: "YOUR_API_KEY",
      authDomain: "YOUR_PROJECT.firebaseapp.com",
      databaseURL: "https://YOUR_PROJECT-default-rtdb.firebaseio.com",
      projectId: "YOUR_PROJECT"
    };

    const app = initializeApp(firebaseConfig);
    const db = getDatabase(app);
    const telemetryRef = ref(db, "telemetry/live");
    const bulbRef = ref(db, "controls/bulbState");

    // Live sensor values
    onValue(telemetryRef, (snapshot) => {
      const d = snapshot.val();
      if (!d) return;
      document.getElementById("temp").textContent = d.temperature;
      document.getElementById("hum").textContent = d.humidity;
      document.getElementById("light").textContent = d.light;
    });

    // Keep the toggle in sync with the database
    onValue(bulbRef, (snapshot) => {
      document.getElementById("bulbToggle").checked = snapshot.val() === 1;
    });

    // Send the toggle change to the database
    document.getElementById("bulbToggle").addEventListener("change", (e) => {
      set(bulbRef, e.target.checked ? 1 : 0);
    });
  </script>
</body>
</html>
12 • Architectural Breakdown

12. Code Breakdown & Modular API Architecture

initializeApp(firebaseConfig)
Parses project credentials and establishes the runtime connection to Google Firebase cloud services.
getDatabase(app)
Initializes the Realtime Database client instance and opens the persistent WebSocket communication channel.
Database Path Pointers (ref)
Creates deterministic pointers targeting specific nodes: telemetry/live and controls/bulbState.
Reactive Listener (onValue)
Subscribes to live sensor updates, invoking the callback with an immutable data snapshot whenever cloud values mutate.
Snapshot Parsing (snapshot.val())
Deserializes the JSON snapshot payload into a native JavaScript object containing temperature, humidity, and light.
Database Mutation (set)
Translates user checkbox toggling into binary integer updates (1 or 0), committing mutations to the cloud database.

14 • Engineering Insights

14. Key Learnings

Shared Cloud State Layers
A cloud database decouples interfaces from physical hardware. The browser and ESP32 never connect directly; they synchronize through shared data nodes.
Push-Based WebSockets
Replacing client-side polling with reactive event subscriptions (onValue) slashes network bandwidth while delivering instantaneous UI updates.
Modular SDK Optimization
Leveraging the modern Firebase v10 modular API ensures clean code organization without importing bloated legacy client libraries.
Independent Frontend Testing
Simulating sensor updates directly in the Firebase Console proves that frontend logic is bulletproof before embedded hardware integration.
15 • Operational Delivery

15. Final Result & Engineering Takeaway

Task 04 successfully delivered a fast, responsive, and robust cloud-connected web portal:

PRODUCTION VERIFIED
Live Telemetry & Actuation Portal
The web dashboard renders live Temperature, Humidity, and Light Level updates instantly as data mutates in the cloud. Flipping the Bulb State toggle commits 1 or 0 directly to the database. The entire client application is hosted on Google's edge infrastructure at Smart Home Dashboard.

Core Takeaway: The value of Task 04 lies in decoupling user interfaces from embedded hardware using cloud databases as shared state abstractions. Neither tier needs to understand the internal mechanisms of the other: the browser does not need to know GPIO pin mappings, and the microcontroller does not need to know DOM structures. Firebase serves as the universal synchronization layer.
