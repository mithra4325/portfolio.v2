01 • System Blueprint

1. Overview

The purpose of Task 04 was to engineer a browser-based IoT monitoring and control dashboard powered by Firebase Realtime Database and deployed globally via Firebase Hosting.

The web application displays real-time ambient telemetry—specifically Temperature, Humidity, and Light Level—and provides a real-time binary toggle switch for an electrical Bulb. Rather than forcing the browser to maintain a fragile peer-to-peer connection with embedded microcontroller silicon, the frontend connects directly to Firebase using the official Firebase JavaScript SDK v10.

Figure 4.1 — Complete 3-Tier Data Synchronization Pipeline: Web Browser DOM Bindings, Firebase RTDB Cloud State, and ESP32 Physical Tier.
CLIENT TIER
Reactive Web Interface
Constructed purely in vanilla HTML/CSS/JS. Binds directly to DOM targets using onValue() event listeners to render incoming environmental values without page refreshes.
CLOUD TIER
Shared Cloud Database State
Firebase Realtime Database persists the shared JSON tree, managing bidirectional WebSocket channels that broadcast mutations instantaneously across connected subscribers.
EDGE TIER
Physical Hardware Node
The ESP32 microcontroller reads physical transducers (DHT11, LDR) and executes relay actuation, communicating exclusively through cloud database endpoints.

STEP 2

STEP 3
Reactive Transition to Main Dashboard
The onAuthStateChanged observer fires immediately, hiding the login screen, unmasking the dashboard grid, establishing the Realtime Database listeners, and initiating background telemetry logging.

05 • Cloud Data Contract

5. Firebase Database Structure

The database schema is organized as a shallow, deterministic JSON hierarchy partitioning read-only telemetry from write-enabled control parameters:

Figure 4.3 — Firebase Realtime Database JSON Schema Tree: Structured Partitioning of Telemetry Streams and Actuator Directives.
PATH: telemetry/live/
Read-Only Telemetry Partition
Contains current environmental sensor outputs (temperature, humidity, light). Consumed by the web dashboard as read-only event streams. Written exclusively by microcontroller firmware.
PATH: controls/bulbState
Read-Write Actuation Partition
Holds the target binary actuator state (1 = ON, 0 = OFF). Mutated by the dashboard toggle switch and consumed by the ESP32 relay driver.
06 • Dual Communication Pipeline

6. Complete Data Flow Pipeline

The system maintains two independent, non-interfering data streams across the shared cloud database:

Figure 4.4 — Dual Operational Pathways: Asynchronous Downlink Telemetry Ingestion vs Instantaneous Uplink Actuation.
STREAM A
Downlink Sensor Telemetry Pipeline
Sensors sample ambient physical conditions → ESP32 serializes JSON → Pushes to telemetry/live → Firebase broadcasts over WebSocket → onValue() unblocks → DOM text nodes update.
STREAM B
Uplink Actuator Control Pipeline
User clicks Bulb Toggle → change event fires → set(bulbRef, 1 or 0) mutates database → Cloud updates controls/bulbState → Hardware listener catches event → Relay switches AC load.
07 • Protocol Architecture

7. Reactive Event Streaming vs HTTP Polling

Traditional web architectures often query REST APIs using periodic setInterval() polling loops. This approach incurs heavy HTTP header overhead, wastes mobile client bandwidth, and produces choppy, delayed UI rendering.

Figure 4.5 — Protocol Comparison: Traditional HTTP Polling vs Firebase Reactive WebSocket Push Architecture.
Traditional HTTP Polling (Obsolete)
Dispatches repetitive GET requests every N seconds. Massive TCP handshake overhead, redundant empty responses, battery drain, and inevitable notification latency.
Firebase Reactive Streams (Task 4)
Maintains a single persistent WebSocket connection. Zero idle bandwidth. The cloud server pushes byte payloads strictly when database values mutate.

// =========================================================

import { initializeApp } from "https://www.gstatic.com/firebasejs/10.12.2/firebase-app.js";
import {
  getAuth,
  signInWithEmailAndPassword,
  signInWithPopup,
  GoogleAuthProvider,
  signOut,
  onAuthStateChanged
} from "https://www.gstatic.com/firebasejs/10.12.2/firebase-auth.js";
import {
  getDatabase,
  ref,
  onValue,
  set,
  push,
  query,
  limitToLast,
  serverTimestamp
} from "https://www.gstatic.com/firebasejs/10.12.2/firebase-database.js";

// Firebase Configuration (Placeholders for public repository)
const firebaseConfig = {
  apiKey: "YOUR_FIREBASE_API_KEY",
  authDomain: "mithra-63101.firebaseapp.com",
  databaseURL: "https://mithra-63101-default-rtdb.firebaseio.com",
  projectId: "mithra-63101",
  storageBucket: "mithra-63101.firebasestorage.app",
  messagingSenderId: "649689915283",
  appId: "YOUR_FIREBASE_APP_ID"
};

const app = initializeApp(firebaseConfig);
const auth = getAuth(app);
const db = getDatabase(app);

// Authentication: Email/Password & Google Sign-In
const loginForm = document.getElementById("login-form");
const googleLoginBtn = document.getElementById("google-login-btn");
const logoutBtn = document.getElementById("logout-btn");

if (loginForm) {
  loginForm.addEventListener("submit", (e) => {
    e.preventDefault();
    const email = document.getElementById("email").value.trim();
    const password = document.getElementById("password").value;
    signInWithEmailAndPassword(auth, email, password)
      .catch(err => alert("Login failed: " + err.message));
  });
}

if (googleLoginBtn) {
  const provider = new GoogleAuthProvider();
  googleLoginBtn.addEventListener("click", () => {
    signInWithPopup(auth, provider).catch(err => alert("Google Sign-In failed"));
  });
}

if (logoutBtn) {
  logoutBtn.addEventListener("click", () => signOut(auth));
}

// Reactive Screen Router
onAuthStateChanged(auth, (user) => {
  if (user) {
    document.getElementById("login-screen").classList.add("hidden");
    document.getElementById("dashboard-screen").classList.remove("hidden");
    startListening();
  } else {
    document.getElementById("login-screen").classList.remove("hidden");
    document.getElementById("dashboard-screen").classList.add("hidden");
  }
});

// Real-Time Database Event Listeners
function startListening() {
  onValue(ref(db, "smartHome/temperature"), (snap) => {
    const val = snap.val();
    if (val !== null) document.getElementById("temp-value").textContent = val;
  });

  onValue(ref(db, "smartHome/humidity"), (snap) => {
    const val = snap.val();
    if (val !== null) document.getElementById("humidity-value").textContent = val;
  });

  onValue(ref(db, "smartHome/light"), (snap) => {
    const val = snap.val();
    if (val !== null) {
      document.getElementById("light-value").textContent = val;
      const pct = Math.min(100, Math.round((val / 1023) * 100));
      document.getElementById("light-bar-fill").style.width = pct + "%";
    }
  });

  onValue(ref(db, "smartHome/bulb"), (snap) => {
    const isOn = snap.val() === true;
    const statusEl = document.getElementById("bulb-status");
    statusEl.textContent = isOn ? "ON" : "OFF";
    statusEl.style.color = isOn ? "#16a34a" : "#dc2626";
    document.getElementById("bulb-icon").textContent = isOn ? "💡" : "⚪";
  });

  // Relay Controls Mutation Handlers
  document.getElementById("bulb-on-btn")?.addEventListener("click", () => {
    set(ref(db, "smartHome/bulb"), true);
  });
  document.getElementById("bulb-off-btn")?.addEventListener("click", () => {
    set(ref(db, "smartHome/bulb"), false);
  });
}

14 • Diagnostics & Solutions

14. Problems Encountered & Engineering Solutions

Developing a reactive cloud dashboard that synchronizes asynchronously with Firebase services introduced several real-world software engineering challenges:

DEFENSIVE PARSING
1. Initial Null Snapshot Crash
Symptom: On initial web app boot prior to telemetry ingestion, snapshot.val() returned null, causing uncaught JavaScript runtime exceptions (TypeError: Cannot read properties of null) when attempting to access property fields.
Resolution: Implemented defensive null-guard clauses and modern nullish coalescing operators (val?.temperature ?? "--") across all reactive callback listeners, guaranteeing that uninitialized paths render placeholder dashes without freezing the DOM.
ROUTING LIFECYCLE
2. Auth State Redirection Flicker
Symptom: When a user refreshed the page while authenticated, the login card briefly flashed for ~150ms before the dashboard rendered, causing an annoying visual layout shift.
Resolution: Configured #dashboard-screen with default class="hidden" in static CSS and centralized all DOM transition logic inside onAuthStateChanged(auth, callback), ensuring UI components reveal only after token validation resolves.
CANVAS MEMORY REUSE
3. Chart.js Re-Render Memory Conflict
Symptom: Subscribing the Chart.js canvas to the historical telemetry log triggered "Canvas is already in use. Chart with ID '0' must be destroyed before the canvas can be reused" on every 30-second snapshot update.
Resolution: Tracked the chart instance globally and executed if (historyChart) { historyChart.destroy(); } immediately prior to instantiating new datasets, releasing canvas memory buffers cleanly.
DATABASE SECURITY
4. Realtime Database Security Rules Lockout
Symptom: Firebase Realtime Database default locked rules rejected all client requests with PERMISSION_DENIED, blocking the browser from reading telemetry or writing bulb commands.
Resolution: Authored deterministic JSON security rules requiring valid user authentication (".read": "auth != null", ".write": "auth != null"), linking permissions directly to the Firebase Auth token.
STATE ISOLATION
5. Auto vs Manual Threshold Race Condition
Symptom: When the dashboard was switched to Automatic Mode, manual button clicks on Bulb ON/OFF produced a race condition against light-sensor threshold rules.
Resolution: Injected conditional UI disabling: setting smartHome/mode to "auto" automatically sets bulbOnBtn.disabled = true and bulbOffBtn.disabled = true, preventing conflicting control signals.
15 • Engineering Insights

15. Key Learnings

Shared Cloud State Layers
A cloud database decouples interfaces from physical hardware. The browser and ESP32 never connect directly; they synchronize through shared data nodes.
Push-Based WebSockets
Replacing client-side polling with reactive event subscriptions (onValue) slashes network bandwidth while delivering instantaneous UI updates.
Modular SDK Optimization
Leveraging the modern Firebase v10 modular API ensures clean code organization without importing bloated legacy client libraries.
Independent Frontend Testing
Simulating sensor updates directly in the Firebase Console proves that frontend logic is bulletproof before embedded hardware integration.
