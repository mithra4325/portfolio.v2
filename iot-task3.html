TASK 03 VOICE AUTOMATION GOOGLE ASSISTANT & IFTTT MQTT ACTIVE-LOW RELAY

Voice Control with Google Assistant and IFTTT

Chaining smartphone conversational natural language recognition, cloud webhooks, Adafruit IO MQTT broker, and ESP32 active-LOW optocoupled relay switching for hands-free AC appliance automation.

1. Overview

The objective of this third task was to implement hands-free, natural voice control over physical AC appliances by chaining specialized cloud automation platforms with an embedded microcontroller.

In this architecture, the user speaks a natural phrase to Google Assistant on a smartphone. Google Assistant performs speech recognition and forwards the matched intent to an IFTTT (If This, Then That) automation applet. The applet updates a designated feed named bulb on Adafruit IO, which acts as the cloud MQTT broker.

An ESP32 development board connected to the local Wi-Fi subscribes to this MQTT feed over port 1883. When a new ON or OFF payload arrives, the ESP32 interprets the message and toggles GPIO 23. GPIO 23 drives an electromechanical relay module operating on active-LOW logic, which safely switches the power line to an electrical appliance or bulb.

The physical electrical load whose line circuit is completed through the relay's COM and NO contacts.

6. Hardware Connections

The physical circuit consists of two galvanically separated zones: a low-voltage DC control side and a switched appliance load side:

Figure 3.2 — Optocoupled Relay Module Schematic & Dual-Domain Electrical Isolation
⚙
Low-Voltage DC Control Domain
ESP32 GPIO 23 • 3.3V Logic Level
Directly sinks current through the relay optocoupler input. Powered by external 5V rail for coil energization without drawing heavy switching currents from ESP32 3.3V LDO.
⚡
High-Voltage AC Mains Domain
230V AC • Electromechanical Galvanic Isolation
Switches phase/live line across COM and NO terminals. Protected by optoisolator (5kV breakdown) and flyback diode to quench inductive switching transients.

Operating Principle: Under quiescent conditions (relay de-energized), the Common (COM) and Normally Open (NO) contacts remain mechanically separated, breaking the appliance circuit. When GPIO 23 is driven LOW, the relay coil energizes, pulling the internal armature to bridge COM and NO, completing the appliance circuit.

Electrical Safety Notice
CRITICAL: Mains Voltage Precautions
Interfacing microcontrollers with AC appliances involves hazardous voltages that can cause severe shock or fire if mishandled:
  • Disconnect Mains Before Wiring: Never adjust, touch, or inspect load wiring while the AC source is energized.
  • Physical Segregation: Maintain generous physical spacing between low-voltage DC logic wires (ESP32) and high-voltage AC conductors.
  • No Exposed Conductors: All AC connections must be fully terminated inside insulated terminal blocks or enclosed junction boxes with strain relief.
  • Relay Contact Ratings: Ensure the relay module's contact rating (e.g. 10A @ 250V AC) safely exceeds the steady-state and inrush current of the load.
  • Professional Verification: When testing with AC mains power, have wiring inspected by a qualified professional before applying electrical power.

10. Adafruit IO Layer

Adafruit IO serves as the cloud database and MQTT broker in this architecture:

☁
Topic Mapping & Feed Abstraction
Cloud Feed Name: bulb
MQTT Full Topic Path: USERNAME/feeds/bulb
Broker Endpoint: io.adafruit.com:1883 (Plain TCP) / 8883 (TLS)

When IFTTT writes a new value to the bulb feed via REST, Adafruit IO immediately publishes that value to the corresponding MQTT topic. Any authorized client subscribed to USERNAME/feeds/bulb receives the payload instantly over its established TCP connection.

This abstraction decouples the frontend entirely: the ESP32 does not know whether the feed update originated from an IFTTT voice applet, an Adafruit IO web dashboard, or a REST API call.

11. MQTT Communication Layer

Key Protocol Details:

  • Role: In this task, the ESP32 acts strictly as an MQTT subscriber. It does not publish telemetry or voice status back to the broker.
  • Persistent Connection: The ESP32 maintains an open TCP socket to io.adafruit.com:1883, eliminating the repeated handshake and header overhead of HTTP.
  • Keep-Alive Ping: The firmware issues periodic mqtt.ping() calls every 30 seconds to prevent broker timeout and socket termination.

12. ESP32 Firmware

The embedded firmware manages network association, broker connectivity, and GPIO actuation across a disciplined lifecycle:

  1. Serial Initialization: Starts hardware UART at 115200 baud for debugging.
  2. Safe Boot Configuration: Sets pinMode(RELAY_PIN, OUTPUT) and immediately drives digitalWrite(RELAY_PIN, RELAY_OFF). Setting the pin to HIGH on boot prevents the active-LOW relay from momentarily pulsing ON during power-up.
  3. Wi-Fi Association: Connects to the local 2.4 GHz access point using WiFi.begin() and blocks until connected.
  4. Feed Subscription: Registers the subscription handle mqtt.subscribe(&bulbFeed).
  5. MQTT Broker Connection: Connects to io.adafruit.com with automated retry and restart logic if disconnected.
  6. Subscription Event Loop: Checks for new incoming packets using mqtt.readSubscription(1000).
  7. Payload Parsing & Switching: Trims and capitalizes the payload string, comparing against "ON" to drive GPIO 23.

13. Relay Control

The relay module utilized in this project operates on active-LOW logic. Understanding and accommodating this inversion in firmware is vital: 

#define RELAY_ON  LOW   // Driving GPIO 23 to 0V (GND) energizes the relay optocoupler
#define RELAY_OFF HIGH  // Driving GPIO 23 to 3.3V (VCC) de-energizes the relay optocoupler
State Transition Mapping
⚡
Payload: "ON"
GPIO Output: digitalWrite(23, LOW) (0V)
Optocoupler: LED Sinks Current → Phototransistor ON
Coil State: 5V Coil Energizes → Armature Pulls Down
Contacts: COM-NO Closed Loop → APPLIANCE ON
◼
Payload: "OFF"
GPIO Output: digitalWrite(23, HIGH) (3.3V)
Optocoupler: Zero Potential Difference → LED OFF
Coil State: Coil De-energizes → Spring Releases Armature
Contacts: COM-NO Open Circuit → APPLIANCE OFF

Many standard 5V optocoupler relay boards use active-LOW inputs because the optocoupler's internal infrared LED is tied to VCC; pulling the input pin LOW sinks current through the LED, turning on the internal phototransistor and triggering the relay coil.

15. What Happens When I Say ON?

  1. Acoustic Input: The user speaks the configured ON trigger phrase into Google Assistant on their phone.
  2. Intent Recognition: Google Assistant's speech engine matches the utterance against the registered IFTTT trigger.
  3. IFTTT Execution: IFTTT executes the ON applet, dispatching an automated update to Adafruit IO.
  4. Feed Update: Adafruit IO writes ON to the bulb feed.
  5. MQTT Publish: Adafruit IO's broker sends the MQTT message to all subscribers of USERNAME/feeds/bulb.
  6. ESP32 Reception: In loop(), mqtt.readSubscription(1000) receives the packet.
  7. String Normalization: The firmware reads the payload into a String, trims whitespace, and converts to uppercase: "ON".
  8. GPIO Actuation: The ternary check msg == "ON" ? RELAY_ON : RELAY_OFF selects RELAY_ON (which evaluates to LOW). digitalWrite(23, LOW) is executed.
  9. Relay Energization: Current flows through the relay optocoupler, energizing the coil and closing the Normally Open (NO) contact.
  10. Physical Illumination: The AC circuit completes and the appliance or bulb illuminates.

16. What Happens When I Say OFF?

  1. Acoustic Input: The user speaks the configured OFF trigger phrase to Google Assistant.
  2. Intent Recognition: Google Assistant identifies the OFF intent and notifies IFTTT.
  3. IFTTT Execution: IFTTT triggers the OFF applet and sends data to Adafruit IO.
  4. Feed Update: Adafruit IO updates the bulb feed with the string OFF.
  5. MQTT Publish: The broker distributes the OFF payload to the ESP32.
  6. ESP32 Reception: The ESP32 receives the message during its subscription poll.
  7. String Normalization: The message is normalized to uppercase: "OFF".
  8. GPIO Actuation: The check fails the "ON" comparison, selecting RELAY_OFF (HIGH). digitalWrite(23, HIGH) is executed.
  9. Relay Release: Sinking current ceases; the coil de-energizes and the spring forces the contact open.
  10. Physical Turn Off: The circuit is broken and the appliance extinguishes.

17. Implementation Process

  1. Feed Setup on Adafruit IO: Logged into Adafruit IO and created a new feed titled bulb.
  2. Google Assistant Trigger Definition: Linked Google Assistant with IFTTT and defined the spoken trigger phrases for ON and OFF operations.
  3. IFTTT Applet Construction: Created two independent applets connecting Google Assistant phrases to Adafruit IO feed actions (sending ON and OFF).
  4. Hardware Assembly (Power Disconnected): Wired the relay module DC inputs (IN1 to GPIO 23, VCC to 5V, GND to ESP32 ground). Wired the appliance line through relay COM and NO terminals with mains power physically disconnected.
  5. Firmware Configuration: Authored the sketch in Arduino IDE, specifying Wi-Fi credentials, Adafruit IO username, secret AIO key, relay pin definition, and active-LOW constants.
  6. Sketch Upload: Flashed the firmware to the ESP32 development board over USB.
  7. Connection Verification: Monitored the Serial Monitor at 115200 baud to verify successful Wi-Fi handshake and MQTT broker connection.
  8. Voice Testing (ON): Spoke the configured ON phrase to Google Assistant; observed the IFTTT log, Serial Monitor output (Voice command received: ON), relay click, and appliance illumination.
  9. Voice Testing (OFF): Spoke the OFF phrase; confirmed relay release and appliance turn-off.
  10. End-to-End Cycle Validation: Repeated consecutive ON and OFF voice commands to confirm multi-hop reliability and persistent MQTT keep-alive operation.

Consequently, response time is not instantaneous. Latency is governed by cumulative network factors:

  • Acoustic processing and speech intent recognition latency on Google's cloud servers.
  • Webhook execution and polling intervals on IFTTT's automation engine.
  • REST API ingestion and internal feed publication within Adafruit IO.
  • Internet routing and Wi-Fi propagation delay to the ESP32.
  • ESP32 subscription loop polling interval (mqtt.readSubscription(1000)).

Observed response occurred within a short delay, but no formal latency benchmark was recorded. In production IoT systems, multi-hop cloud dependencies prioritize hands-free convenience over deterministic real-time latency.

20. Failure Points and Troubleshooting

Chaining multiple independent services creates multiple failure boundaries across the control chain:

Google Assistant Does Not Trigger
Verify exact phrase matching, ensure the smartphone is logged into the same Google account linked with IFTTT, and check internet connectivity.
IFTTT Applet Fails to Execute
Inspect IFTTT Applet Activity Logs to determine if the trigger fired. Verify authorized permissions between Google Assistant and Adafruit IO services.
Adafruit IO Feed Not Updating
Check Adafruit IO feed history online. Verify that the feed name in IFTTT exactly matches bulb and confirm AIO key validity.
ESP32 Fails to React to Feed
Monitor Serial Monitor at 115200 baud. Confirm active Wi-Fi and MQTT connection. Ensure the subscription topic format is AIO_USERNAME "/feeds/bulb".
Relay Logic Inverted
If the relay turns ON when saying OFF, confirm active-LOW constants: RELAY_ON = LOW and RELAY_OFF = HIGH.
Relay Pulses ON During Boot
Ensure digitalWrite(RELAY_PIN, RELAY_OFF); executes immediately following pinMode() in setup() before Wi-Fi is initialized.

21. Security Considerations

Deploying cloud-connected embedded devices requires strict credential hygiene:

  • API Key Protection: The Adafruit IO Key (AIO_KEY) grants read and write access to all feeds in the account. It must be treated as a sensitive secret and never committed to public version control.
  • Credential Placeholders: In public portfolio repositories and documentation sketches, sensitive constants are replaced with placeholders (YOUR_WIFI_NAME, YOUR_WIFI_PASSWORD, YOUR_AIO_USERNAME, YOUR_AIO_KEY).
  • Voice Authentication: Voice control relies on Google Assistant's voice-match model on the personal smartphone, preventing unauthorized nearby speakers from triggering appliance switching.
  • Network Isolation: IoT devices should ideally reside on dedicated 2.4 GHz guest or IoT subnets isolated from primary personal computers.

23. Complete Firmware Code

File: ESP32_Voice_Relay.ino
#include <WiFi.h>
#include "Adafruit_MQTT.h"
#include "Adafruit_MQTT_Client.h"

#define WLAN_SSID      "YOUR_WIFI_NAME"
#define WLAN_PASS      "YOUR_WIFI_PASSWORD"
#define AIO_SERVER     "io.adafruit.com"
#define AIO_SERVERPORT 1883
#define AIO_USERNAME   "YOUR_AIO_USERNAME"
#define AIO_KEY        "YOUR_AIO_KEY"

const int RELAY_PIN = 23;   // relay IN1
const int RELAY_ON  = LOW;  // most relay modules are active-LOW
const int RELAY_OFF = HIGH;

WiFiClient client;
Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, AIO_SERVERPORT, AIO_USERNAME, AIO_KEY);
Adafruit_MQTT_Subscribe bulbFeed = Adafruit_MQTT_Subscribe(&mqtt, AIO_USERNAME "/feeds/bulb");

unsigned long lastPing = 0;

void MQTT_connect() {
  if (mqtt.connected()) return;
  Serial.print("Connecting to MQTT... ");
  int8_t ret;
  uint8_t retries = 3;
  while ((ret = mqtt.connect()) != 0) {
    Serial.println(mqtt.connectErrorString(ret));
    mqtt.disconnect();
    delay(5000);
    if (--retries == 0) ESP.restart();
  }
  Serial.println("connected");
}

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);
  digitalWrite(RELAY_PIN, RELAY_OFF);   // relay off at start

  WiFi.begin(WLAN_SSID, WLAN_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("\nWiFi connected");

  mqtt.subscribe(&bulbFeed);
}

void loop() {
  MQTT_connect();

  Adafruit_MQTT_Subscribe *sub;
  while ((sub = mqtt.readSubscription(1000))) {
    if (sub == &bulbFeed) {
      String msg = (char *)bulbFeed.lastread;
      msg.trim();
      msg.toUpperCase();
      Serial.print("Voice command received: ");
      Serial.println(msg);
      digitalWrite(RELAY_PIN, msg == "ON" ? RELAY_ON : RELAY_OFF);
    }
  }

  if (millis() - lastPing > 30000) {
    lastPing = millis();
    if (!mqtt.ping()) mqtt.disconnect();
  }
}

27. Task 03 Takeaway

The core engineering achievement of Task 3 was not simply toggling a relay with voice, but orchestrating multiple specialized platforms into a unified, reliable control chain:

  • Google Assistant solves the natural language problem.
  • IFTTT solves the cross-platform integration problem.
  • Adafruit IO solves the cloud message routing problem.
  • MQTT solves the low-overhead delivery problem.
  • ESP32 solves the hardware logic problem.
  • Relay Module solves the high-voltage electrical switching problem.

Real-world IoT engineering relies on composing specialized tools rather than building every capability from scratch. By decoupling interface, cloud routing, and device actuation, the system achieved sophisticated capabilities with lean, dependable embedded firmware.
